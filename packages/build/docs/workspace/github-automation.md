# GitHub automation

A workspace can own two kinds of GitHub Actions workflow, and they want
opposite treatment.

The **pipeline** — `ci.yml`, `release.yml` — is long-lived and hand-tuned. It
carries comments, advisory `continue-on-error` lanes, matrix jobs, and platform
lanes no declaration reproduces. Generating it is a downgrade even when the
generator is correct. [GithubCiGen](../reference/targets/github-ci-gen.md)
therefore defaults to `contract` mode: it reads the checked-in file and fails
when a declared gate stops running.

The **automation** — the event-driven workflows that react to issues, comments,
and pull requests — is the other case. Each is small, written once, and read
rarely, and each is where a mistake is expensive: an automation job that reads
an issue body and holds a credential is a supply-chain hole with a friendly
name. [GithubAutomation](../reference/targets/github-automation.md) owns those
files outright, renders them from a declaration, and byte-checks them under
`ci`.

## What a declaration looks like

```ts
export const issueIntake = Smithers.GithubAutomation({
  slug: "issue-intake",
  target: "issueIntake",
  workflowName: "Issue intake",
  packageManager,
  on: { issues: ["opened", "edited"] },
  concurrency: "gen-issue-intake-${{ github.event.issue.number }}",
  jobs: [
    Smithers.Automation.agent({
      id: "intake",
      entry: "intake.ts",
      requireApproval: true,
      permissions: { contents: "write", issues: "write" },
      secrets: [anthropicKey],
      env: { GH_TOKEN: "${{ github.token }}" }
    })
  ]
})
```

`slug` decides the file. The output is `.github/workflows/gen.<slug>.yml`, and
it is not separately declarable: a generated file whose path is free to
disagree with its declaration is a generated file the drift gate points at the
wrong place.

## The generated file names its generator

```yaml
# GENERATED by //:issueIntake. Do not edit. Edit BUILD.ts and run smthrs run //:issueIntake.
```

A header that only says "do not edit" sends the reader looking for the
generator. This one hands it over, and the command it names is the one that
works: `build` and `lint` both see check mode, so `smthrs ci` reports drift and
never repairs it, and `smthrs run //:<target>` is the only writer.

## The safety property

A job that reads untrusted text declares `untrustedInput: true`, and the
renderer forces a maintainer gate, strips every credential, skips the agent
CLI install, and pins the job to read-only permissions with a credential-free
checkout. The gate also admits `schedule` and `workflow_dispatch` runs, which
carry no untrusted actor. A declaration that passes a secret into such a job
does not render a weaker workflow; it does not render at all.

A trusted job that only reads a fork pull request's diff subscribes to
`pullRequestTarget`, not `pullRequest`: the fork run of `pull_request` gets no
secrets and a read-only token, while `pull_request_target` keeps them and
checks out the base branch, so the job cannot execute the fork's code by
construction.

That refusal is what lets an automation layer execute a stranger's code safely.
The pattern it produces is a three-job split:

1. a gated job that holds the credential and prepares the work,
2. a sandbox job, `untrustedInput`, that runs it and can only write an
   artifact,
3. a gated job that reads the artifact and does the talking.

The middle job is the one running attacker-influenced code, and it is the one
holding nothing.

## Adding a workflow to this repository

1. Declare it in the root `BUILD.ts` with a unique `slug` and a `target` equal
   to the export name.
2. Run `smthrs run //:<target>` once and commit the generated file.
3. Add the file to `ci.yml`'s `actionlint` argument list. The wiring gate in
   `apps/server/scripts/canary/workflow-wiring.test.ts` fails on a workflow
   that is not linted.
4. Write the entry under `factory/automation/`. It runs the same way from a
   terminal and from Actions; see `factory/automation/README.md`.

## What the flows repository runs

Seven generated workflows drive the software factory's GitHub side: issue
intake, the proof-of-concept loop, the reporter-reply state machine, the repro
proof gate, pull-request review, verified-repro-to-pull-request, and a
scheduled re-verification sweep. The process behind them is in the spec vault
under `Concepts/Github Automation.md`; the entries are in
`factory/automation/`.

`ci.yml` and `release.yml` stay hand-written, and both are verified in place by
`GithubCiGen` in contract mode.
