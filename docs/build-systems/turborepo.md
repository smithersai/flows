# Turborepo for flows

What it looks like to automate this repository with Turborepo 2.10.11, and how
that compares to the in-repo build system (`BUILD.ts`, `@smthrs/targets`,
`@smthrs/build`, `@smthrs/build-cli`). Every claim below was executed in this
worktree; the numbers are from a 16-core aarch64 macOS host with 29 GB free
memory.

## 2. How Turborepo models what `BUILD.ts` models

### Target definition

`BUILD.ts`: a target is a typed TypeScript value with declared inputs,
outputs, toolchain, and secrets. A label addresses it (`//packages/engine:lib`).

Turborepo: a target is a `(package, script)` pair. The task definition in
`turbo.json` carries inputs, outputs, env, and dependency edges; the command
itself lives in the package's `package.json` scripts and is opaque to Turbo —
it schedules `pnpm run <script>` and never knows what the script does. There
is no label syntax beyond `package#task` and `//#task` for the root.

### The toolchain

`BUILD.ts`: declared as values — `Smithers.Runtime.Node({ version: ">=22.19.0" })`,
`Smithers.PackageManager.Pnpm({ version: "11.21.0", runtime })` — and threaded
into every target. The Runtime service measures the host and refuses to
execute on a mismatch.

Turborepo: no toolchain model. Turbo infers the package manager from the
`packageManager` field (its `turbo info` here misreports `pnpm9` against pnpm
11.21.0 — cosmetic, but it shows inference rather than declaration). The Node
version, the pnpm version, and the Rust toolchain from `rust-toolchain.toml`
never enter a cache key unless you add them yourself. This setup puts
`rust-toolchain.toml` in `globalDependencies` so a toolchain change rekeys
every task, but nothing stops a developer on Node 20 from poisoning a cache
that Node 22 produced. The `engines` field is advisory metadata to Turbo, not
an enforced requirement.

### Inputs, outputs, and cache keys

`BUILD.ts`: inputs are declared per target as typed values (files, globs,
other targets' outputs, secrets-by-name). The key is a hash of the declared
closure.

Turborepo: inputs are git-aware file globs per task, plus declared env vars,
plus `globalDependencies`, plus a hash of external dependency versions parsed
from the lockfile. Outputs are globs; on a hit, Turbo restores them and
replays the captured logs. Measured here:

| Scope | Tasks | Cold | Warm |
| --- | --- | --- | --- |
| `build` | 44 | 41.35s | 41ms (`FULL TURBO`) |
| `check` + `lint` + `circular` | 137 | 2m46.6s | 105ms (`FULL TURBO`) |
| `test` (`--concurrency=2`) | 51 | 3m15.8s | 97ms (`FULL TURBO`) |
| Root gates (`browser`, `test:scripts`, `docs`, `cargo:fmt`) | 4 | 3.0s | 52ms (`FULL TURBO`) |

The full local cache for all of the above is 13 MB. The test number uses
`--concurrency=2` for the same reason the `smthrs-shadow` job in `ci.yml`
passes `--jobs 2`: the heavy vitest suites carry finite 30s per-test budgets
that full parallelism on a loaded host starves. A first unbounded local run
failed 10 suites that each pass in isolation; that is a property of the
suites, not of either build system, but Turbo's default is to discover it the
hard way.

Two input-modeling facts worth knowing about this repository:

- **No `dependsOn: ["^build"]` anywhere.** The workspace manifests point
  `exports` at `./src/*.ts`, so typecheck, lint, test, and build all resolve
  workspace dependencies to TypeScript *source*. Verified empirically: every
  `dist/` deleted, then `tsc -p tsconfig.json` on `@smthrs/flows` (19
  workspace dependencies) exits 0. The goal's premise that TypeScript project
  references would demand `^build` edges does not hold here — no package
  tsconfig declares `references`. If the repo ever switches to
  dist-resolution, the change is one line in the root `turbo.json`.
- **`build` and `check` write the same directory.** `check` is `tsc -b
  tsconfig.json` (emits `dist/esm` + `dist/tsconfig.tsbuildinfo`) and `build`
  emits `dist/esm` + `dist/cjs`, starting with `rmSync("dist")`. Turbo
  schedules independent tasks of one package concurrently, so `turbo run
  build check` in a single invocation can interleave a delete with an emit.
  There is no per-task sandbox. The CI lane runs them as separate steps; keep
  it that way.

### Macros and target expansion across 45 packages

`BUILD.ts`: `Smithers.PackageDefaults({ directories: "packages/*", macro:
Smithers.StandardPackage })` expands one macro over a directory glob. No
per-package file exists unless the package genuinely differs.

Turborepo: tasks declared once in the root `turbo.json` apply to every
package that has the script, so the uniform 42 packages needed no task
configuration at all. But Boundaries tags exist only as a per-package
`turbo.json` field — there is no root-level glob tagging — so this change
still adds 45 three-line files whose only content is `extends` plus a tag
that duplicates `smthrs.group` from the manifest. Package Configurations
compose cleanly for the packages that differ (`packages/jj`, the apps,
`packages/build/infra`); the boilerplate is the tagging, not the tasks.

### Generated-file drift checks

`BUILD.ts`: `pnpm-workspace.yaml`, the workspace `tsconfig.json`, and
`pnpm-lock.yaml` are *outputs* of targets, and `GithubCiGen` verifies that
`.github/workflows/ci.yml` still runs the declared gates. Editing a generated
file by hand fails the drift check.

Turborepo: no equivalent. Turbo reads all of these files; it generates none
of them and cannot drift-check them. This showed up in practice within
minutes: `pnpm install` on a machine with a global `minimumReleaseAge` policy
auto-appended a `minimumReleaseAgeExclude` block to `pnpm-workspace.yaml`, a
file the in-repo system owns. Nothing in a Turbo setup notices. (The block is
reverted in this PR; the issue-#166 conformance suite in `@smthrs/flows`
byte-pins the file, which is what actually catches it here.)

### Secrets

`BUILD.ts`: `Smithers.Secret("SMITHERS_CACHE_TOKEN")` names the variable; a
substituting proxy swaps an unguessable placeholder for the real value on
outbound requests, so key material records the name and never the value.

Turborepo: `env` puts a variable's value into the task hash (one-way, but it
rekeys the cache on rotation, and the value must be readable to hash it).
`passThroughEnv` makes a variable available to the task without hashing it —
the right tool for secrets, used here for the Cloudflare and cache tokens on
the deploy tasks and for the smithers cache token on `//#docs`. That is the
whole model: declare-or-lose under `envMode: "strict"`, hash-or-don't. There
is no proxying, no redaction guarantee beyond log scrubbing, and no way to
prove from the config which tasks can observe a secret beyond reading every
`passThroughEnv` list by hand. What strict mode *does* buy is real: a task
that reads an undeclared variable gets an empty string, so the stale-cache
class of bug fails loudly instead of silently.

### `node_modules` as a dependency

`BUILD.ts`: `Smithers.Install` makes `node_modules` a target keyed on the
declared toolchain and the generated lockfile. Targets depend on it; the
executor materializes it.

Turborepo: `node_modules` is outside the graph. Turbo assumes you ran
`pnpm install` and folds external dependency *versions* (parsed from the
lockfile) into package hashes. If the install is stale or missing, tasks fail
with module-resolution errors, not with a graph-level "install is out of
date" verdict. Every Turbo CI job starts with an unconditional install step,
which is the accepted workaround.

## 3. Where Turborepo is genuinely better

- **Cache ergonomics per unit of configuration.** One 130-line `turbo.json`
  produced content-addressed caching over 232 tasks with restore-verified
  outputs (`rm -rf packages/canonical/dist` → cache hit → `dist/esm` and the
  tsbuildinfo return in 33ms). The warm-run numbers in the table above are
  the pitch, and they reproduce.
- **`--affected` is the CI feature this repo hand-rolls.** A one-file edit in
  `packages/observability/src/index.ts` narrowed 51 packages to 5
  (`@smthrs/observability` plus its dependent closure: `flows`,
  `engine-harness`, `cli`, `examples`) and 232 tasks to 25, measured with
  `--dry=json`. The base ref is overridable with `TURBO_SCM_BASE`, which the
  workflow uses. The in-repo system has labels and patterns (`//packages/...`)
  but nothing that diffs the SCM and prunes the graph for you.
- **The graph is inspectable without executing it.** `--dry=json` emits every
  task's hash, inputs-with-hashes, and dependency edges; `--graph` renders
  Graphviz/SVG; `--summarize` writes `.turbo/runs/*.json` with per-task
  timing and cache status (uploaded as CI artifacts here); `turbo ls` and
  `turbo query` answer package-graph questions. `turbo query` is real
  GraphQL — `scripts/turbo-engine-boundary.mjs` uses it to assert the
  release-train boundary and prints `engine boundary holds: 23 engine
  packages, 0 agent/tooling dependencies`.
- **Worktree-aware local cache.** In this git worktree, Turbo redirected the
  local cache into the shared git common dir (`.../.git/modules/.turbo/cache`)
  and announced `using shared worktree cache`. Every linked worktree shares
  one local cache — a thoughtful default for exactly the multi-lane setup this
  comparison runs.
- **The dev loop.** `persistent: true` + `interactive: true` model long-lived
  TTY processes (wrangler dev, vite HMR, electrobun) as first-class tasks,
  `turbo watch` reruns the graph on file changes, and `ui: "tui"` makes 45
  concurrent log streams readable. The in-repo executor has no persistent-task
  concept.
- **`turbo prune`.** `turbo prune smithers-server --docker` emitted a 15 MB
  subworkspace: `out/json` (pruned manifests + a pruned `pnpm-lock.yaml`, the
  layer you `pnpm install --frozen-lockfile` in a Docker build) and
  `out/full` (the 20-package source closure). For a Cloudflare deploy this is
  the difference between uploading the monorepo and uploading the closure.
  Caveat: the root package is always in scope, so root devDependencies
  (`@smthrs/build-cli`, `@smthrs/targets`, ...) ride along in the pruned
  lockfile.

## 4. Where Turborepo cannot express what our system expresses

- **Sub-package granularity.** Turbo's unit of caching is the package-task.
  `packages/engine` has ~200 source files; touching one test fixture rekeys
  `test` for the whole package. `BUILD.ts` targets can key on exactly the
  files a rule consumes, and the rule catalog can define finer targets
  (per-suite, per-artifact) without new packages. With Turbo, finer
  granularity means splitting packages — a publishing decision driven by a
  caching concern.
- **The file system is globs, not a graph.** Inputs are patterns evaluated
  against git-tracked files; Turbo does not know that `src/A.ts` imports
  `src/B.ts`, so it cannot invalidate on *actual* read sets. Two consequences
  showed up here. First, over-approximation is the only safe posture: the
  `lint` task uses `$TURBO_DEFAULT$` (every tracked file in the package)
  because `dprint check` reads markdown and JSON as well as source. Second,
  nothing detects that `packages/sync/test/` imports `@smthrs/database` and
  `@effect/platform-node` without declaring them — Turbo hashed those runs
  green because ancestor `node_modules` resolution made them pass.
  (Boundaries *did* flag them; see below.)
- **Overlapping outputs race.** Turbo assumes task outputs are disjoint
  within a package and provides no sandbox. `build` and `check` both emit
  `dist/**` here, and `turbo run build check` can schedule them concurrently.
  A Bazel-like action model (and the in-repo executor) gives each action its
  own declared output set and would call the overlap a conflict at plan time.
- **Root tasks are second-class.** `//#` tasks cannot depend on package
  tasks, so there is no way to say "the browser gate needs the workspace
  built" or "docs parity runs after check". They run standalone, always
  unfiltered by `--affected` in any useful sense (they read the whole repo,
  so their input hash is the whole repo). The five `node --test` gates and
  the browser guard are expressible, but they sit beside the graph rather
  than in it.
- **No toolchain or host modeling.** Covered in §2. Concretely: the wasm
  reproducibility contract ("these bytes only build on
  x86_64-unknown-linux-gnu; refuse elsewhere") is inexpressible. `build:wasm`
  is `cache: false` here because caching it would be actively wrong — a cache
  hit skips the rebuild that *is* the gate, and the committed
  `packages/jj/wasm/flows_jj.wasm` is a drift contract, not a build product.
  Turbo can schedule the script; it cannot say "this task must execute on CI
  even when its inputs are unchanged," which is what the `wasm-repro` job
  means. The cargo gates (`//#cargo:fmt|clippy|test`) cache fine on inputs
  `crates/**` + `Cargo.lock` + `rust-toolchain.toml`, but they inherit the
  same host-blindness: a cache populated on macOS will serve a Linux runner.
  (For fmt/clippy/test verdicts that is mostly harmless; for artifacts it
  would not be.)
- **Boundaries cannot scope to shipped code.** The engine rule is about the
  *published* artifact. Boundaries scans every parseable file, so this repo's
  `BUILD.ts` files (every package imports `@smthrs/targets` — tooling, which
  the tier rules deny) and `eslint.config.js` files (every package imports
  `../../eslint.jsdoc.js` — a path outside the package) account for 182 of
  the 210 findings: 126 tag violations from toolchain imports, 56
  file-leaves-package imports. There is no `include`/`exclude`. The check
  still earned its keep: it surfaced 27 imports of packages never declared in
  the importing package's manifest (`@effect/platform-node` in 18 test files,
  `@smthrs/database` in 4, `@smthrs/targets` in 4 `BUILD.ts` files, a
  `playwright` type import in `apps/ui/scripts/live-store-reset.ts`) and the
  pre-existing circular package dependency `@smthrs/kernel` ↔
  `@smthrs/platform-browser`. But as a release-train gate it is red on a
  compliant repository, which is why `turbo.yml` runs it advisory and the
  query-based script carries the enforcement. The in-repo system scopes
  policy to declared targets, so its equivalent rule has no false-positive
  class.
- **No generated-file ownership.** §2. A Turbo setup cannot make
  `pnpm-lock.yaml` or `ci.yml` outputs of the graph, so it cannot drift-check
  them; the guarantees have to come from elsewhere (here: the issue-#166
  conformance pins, which are tests, not build rules).
- **No secrets model.** §2. `passThroughEnv` is an availability control, not
  a confinement mechanism.
- **Lock-in surface is small but real.** `turbo.json` is declarative JSON:
  no functions, no imports, no types. Anything the schema lacks (a conditional
  output, a computed env list, a per-OS input) is inexpressible rather than
  awkward, and the escape hatch is wrapping scripts — logic that then becomes
  invisible to the cache. `BUILD.ts` is TypeScript; its escape hatch is a
  function call.

## 5. What it costs

- **Dependencies:** one devDependency, `turbo@2.10.11` (plus six platform
  binaries in the lockfile). No runtime footprint; nothing ships.
- **Config surface:** 130 lines of root `turbo.json`, 45 tag files, 8 package
  configurations with real content, one 100-line workflow. The ongoing cost
  is keeping `inputs`/`outputs`/`env` honest as scripts evolve — Turbo cannot
  check them for you, and a wrong glob is a silent cache lie. The repo's
  pin-test culture (issue #166) is the right mitigation and already exists.
- **Vercel-hosted cache by default.** `remoteCache` points at Vercel unless
  `TURBO_API` says otherwise. This PR wires `signature: true`
  (`TURBO_REMOTE_CACHE_SIGNATURE_KEY` signs artifacts HMAC-style so a
  poisoned cache entry fails verification) and leaves the endpoint unset;
  activation is two secrets (`TURBO_TOKEN`, `TURBO_TEAM`) plus the signature
  key. **Could Turbo point at the repo's own cache worker under
  `packages/build/infra`?** Not today. That worker speaks an action-cache /
  CAS protocol (`/ac` JSON documents in D1, content-addressed blobs in R2 —
  see `worker/protocol.ts`). Turbo's remote cache protocol is a different,
  smaller HTTP shape: `GET/PUT /v8/artifacts/:hash` with bearer auth and an
  optional artifact signature. The storage model underneath (hash-keyed
  blobs) is the same, so a thin adapter route in the existing worker — map
  `:hash` to a CAS blob, accept Turbo's auth header — is a day of work, not a
  redesign. Self-hosted open-source servers also exist if Vercel hosting is
  the objection.
- **Pre-existing breakage this PR had to fix to prove itself:** `main` is red
  at `Lint all workspaces` (31 files of dprint drift, fixed in the first
  commit) and the `Documentation parity` step invokes `pnpm exec smthrs`, a
  bin name the build-cli rename removed — the `//#docs` task runs
  `node packages/build-cli/src/main.js docs '//...'` from source instead, the
  same invocation the `smthrs-shadow` job uses.

## 6. What adoption would actually involve

1. Land this PR shape: root `turbo.json`, the tag files, the workflow. Keep
   the recursive pnpm scripts as the fallback path until the turbo lane holds
   a green streak — the same advisory-then-required pattern the
   `smthrs-shadow` job uses.
2. Decide the remote cache question: Vercel (two secrets) or an adapter route
   on the existing worker (small protocol shim, then `TURBO_API` +
   `TURBO_TOKEN`).
3. Triage the Boundaries findings: declare the 27 undeclared imports (real
   hygiene bugs), resolve or accept the `kernel` ↔ `platform-browser`
   package cycle, and either upstream an `include` scope for Boundaries or
   keep the query-based assertion as the enforced form of the engine rule.
4. Move the root gates that can move into package tasks (`//#browser` could
   be a per-package `browser` task on the packages it bundles, which would
   make it affected-filterable and parallel).
5. Accept the two structural gaps or keep the in-repo system for them:
   generated-file drift (`pnpm-workspace.yaml`, the lockfile, `ci.yml`) and
   the wasm reproducibility contract. These are the two places where the
   graph must *own* files rather than read them, and that is the thing Turbo
   does not do.

The honest summary: for scheduling and caching a conventional script graph,
Turborepo is ahead — `--affected`, the TUI, watch mode, prune, query, and the
worktree-shared cache are real, and the warm-run numbers are what they are.
For the properties this repository specifically engineered — typed config,
declared toolchains, generated root files, secrets by name, `node_modules`
as a target, and a reproducibility gate that must never cache — the in-repo
system expresses things Turbo structurally cannot, because Turbo's graph
ends at package scripts and globbed files.
