# 8.7 — approving a request-queue entry never clears it

- **Origin:** https://canary.smithers.sh (bundle `/assets/index-BHHXuMoZ.js`)
- **Account:** `codeplanesmithers` (admin)
- **Repro:** `bun apps/ui/canary-repros/cards/8.7.ts`
- **Screenshot:** `/tmp/canary-cards-8.7-queue.png`
- **Routes:** `POST /api/admin/allowlist`, `GET /api/admin/requests`
- **Selector:** `[data-kind="request-queue"] button:has-text("Approve")`

## Steps

1. Open https://canary.smithers.sh signed in as an admin with at least one
   entry in the request-access queue.
2. Run `/admin.requests`. The card reads `Request-access queue — 1 waiting`.
3. Click **Approve** on the entry.
4. Read `GET /api/admin/requests` again and re-read the card title.

## Expected

The approved login leaves the queue and the card reads `0 waiting`.

## Actual

`POST /api/admin/allowlist` answers HTTP 200 and the card re-reads
`GET /api/admin/requests`, but the entry is still there and the card still reads
`1 waiting`. Pressing Approve is indistinguishable from pressing nothing.

## Root cause

The identity worker's durable store has no command that removes a request.
`~/flows/ui/workers/identity/src/store.ts` implements exactly `requestAccess`,
`listRequests` and `listAudit` (see the `IdentityCommand` union at line 309 and
the switch at 700-736), and the `req:index` record that backs `listRequests` is
only ever appended to. Adding a login to the allowlist does not touch the queue,
so a queue row survives its own approval forever and the card can never show the
approve landing.

## Repro output

```
queue before: ["codeplanesmithers"]
card title: Request-access queue — 1 waiting
approve buttons: 1
POST /api/admin/allowlist -> HTTP 200
queue after: ["codeplanesmithers"]
card title after: Request-access queue — 1 waiting
FAIL 8.7: approving left the queue at 1 entries (was 1); the identity store has no command that removes a request.
```

Exit code 1.

> The Approve button carries no `data-flow` attribute (nor does the
> `grant-confirm` card's Post the grant / Cancel pair), so the repro selects it
> by text. Every visible affordance is supposed to carry one.
