# 1.5 — de-allowlisting does not revoke admin: all ten `admin.*` flows stay registered

- **Origin**: https://canary.smithers.sh
- **Tested**: 2026-08-18
- **Repro**: `bun 1.5.ts` (self-restoring: it re-adds the allowlist row in a `finally`)
- **Screenshot**: `/tmp/canary-access/1.5-nonallowlisted.png`

## Steps

1. Sign in as the test login (`codeplanesmithers`), which is allowlisted and admin.
2. `POST /api/admin/allowlist {"login":"codeplanesmithers","action":"remove"}` — the
   product's own audited door (`apps/server/src/index.ts`, `handleAdmin`).
3. Reload. Read `GET /api/auth/session`, the shell's `data-flows`, and
   `GET /api/admin/requests`.
4. `POST /api/admin/allowlist {"action":"add"}` to restore.

## Expected

`/admin.*` is unregistered for a non-allowlisted account — the flow is absent, not
present-and-refusing.

## Actual

The session comes back `{"login":"codeplanesmithers","allowlisted":false,"admin":true}`
and **nothing is revoked**:

- `data-flows` still lists all ten admin flows: `admin.devtools, admin.allowlist.add,
  admin.allowlist.remove, admin.grant, admin.grant.confirm, admin.grant.cancel,
  admin.requests, admin.queue.approve, admin.feedback, admin.health`
- `GET /api/admin/requests` still answers **HTTP 200** with the real queue, not the
  canonical 404.

Root cause: identity derives `admin` from the `ADMIN_LOGINS` env var, not from the
allowlist (`workers/identity/src/index.ts`, `sessionAnswer` → `adminLogins(env)`), and
both the UI plugin gate and `handleAdmin` read only `session.admin`. So the invariant
"non-allowlisted ⇒ no admin" is a convention about how ADMIN_LOGINS is maintained, not
something the product enforces. Revoking a compromised admin from the allowlist leaves
them full admin.

**Scope note, stated plainly**: the only test login available is in `ADMIN_LOGINS`. A
non-allowlisted login that is *not* in `ADMIN_LOGINS` would get `admin:false` and the
flows would be absent — that variant was not reachable without a second GitHub account
(see the lane summary). What is proven here is that the allowlist is not the gate.

## Selector / route

- `POST /api/admin/allowlist`, `GET /api/admin/requests`, `GET /api/auth/session`
- `[data-flows]` on the app shell
