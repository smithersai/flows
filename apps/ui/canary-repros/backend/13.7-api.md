# 13.7-api — the platform accepts a write addressed by GitHub source coordinates

Backend-level repro of [github/13.7](../github/13.7.md), driven at
<https://api.jjhub.tech> rather than through the SPA, so the defect is pinned to
the Go backend and not to the UI's rendering of it.

- **Target**: `https://api.jjhub.tech` (deployment `smithers-api`, namespace `smithers`)
- **Account**: `smithers-canary` (the `CANARY_API_TOKEN` principal), which has
  imported `octocat/Hello-World`
- **Routes**: `GET /api/repos/{owner}/{repo}`, `POST /api/repos/{owner}/{repo}/issues`
- **Repro**: `CANARY_API_TOKEN=… bun apps/ui/canary-repros/backend/13.7-api.ts`
- **Tested**: 2026-08-20 (backend fix lane)

## Steps

1. `GET /api/repos/octocat/Hello-World`.
2. `POST /api/repos/octocat/Hello-World/issues` with a title and body.

## Expected

The write is refused, naming the repository the caller asked for, the mirror the
row would really have landed in, and the fact that github.com is not reached.
An importable repository is not a writable one.

## Actual

`GET` answers 200 for a repository whose own `full_name` is
`smithers-canary/hello-world` — `LoadRepoContext` resolved the GitHub source
coordinates through the requester's import provenance
(`internal/middleware/repo_context.go`, `resolveRepoBySourceProvenance`).

`POST` then answers **201** and files the issue in that private mirror.
`requireWriteAccess` passes because the caller owns the mirror. The response
body does not name the repository at all, so a client has nothing to catch the
substitution with, and the mirror's numbering is its own — the run below got
`#143` while github.com/octocat/Hello-World is at #10897.

```
GET /api/repos/octocat/Hello-World -> 200 full_name=smithers-canary/hello-world
POST /api/repos/octocat/Hello-World/issues -> 201
{"id":8419,"number":143,"title":"13.7 mirror-alias probe 2026-08-20T00:02:17.921Z", …}

FAIL: the platform accepted an issue on octocat/Hello-World and filed it as
smithers-canary/hello-world#143. github.com/octocat/Hello-World has no such issue.
EXIT=1
```

The repro closes the issue it files, so it leaves no open noise in the mirror.

## Fix

`plue` commit `🐛 fix(repos): refuse writes addressed by GitHub source
coordinates`. `RepoContext` now records the alias, and the issue and landing
write handlers refuse a request that arrived through it with 409 naming both
halves. Reads still follow the alias; the same repository addressed by its own
Smithers coordinates still writes.

**Not yet verified live**: the backend fix lane does not deploy — the serial
deploy stage after it does. This repro exits 1 against the currently deployed
`smithers-api` and is the acceptance check for the rollout.
