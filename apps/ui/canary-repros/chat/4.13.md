# 4.13 — a long transcript wedges the turn seam at HTTP 413, and `/clear` cannot recover it

- **Origin:** https://canary.smithers.sh
- **Tested:** 2026-08-18, signed in as `codeplanesmithers`
- **Route:** `POST /api/agent/turn` (the client re-sends the whole transcript in `messages`)
- **Selectors:** `[data-role]` message bubbles, `.sui-msg-scroller-viewport`, the composer `textarea`
- **Screenshot:** `/tmp/canary-chat-4.13.png`

## Steps

1. Sign in at https://canary.smithers.sh and clear the transcript.
2. Ask for a 1500-word essay seven times in a row (any topics).
3. Then send a trivial prompt, e.g. `say ok`.
4. Then send `/clear`.

## Expected

Row 4.13: "A very long turn (50+ messages) still scrolls smoothly and the
composer stays responsive." A long conversation stays usable, and `/clear` is
always available to start over.

## Actual

**Message count is fine.** A 61-message transcript of short turns scrolls and
types with no lag: composer fill 23ms, ten scroll jumps 6ms, no wedge. That half
of the row passes.

**Payload size is not.** The client re-sends the whole transcript on every turn,
so seven long answers push `POST /api/agent/turn` past the upstream body limit:

```
turn 1 (the printing press): 3 messages, 11686 rendered chars
turn 2 (cartography):        5 messages, 11780
turn 3 (lighthouses):        5 messages, 24061
turn 4 (glassmaking):        7 messages, 38189
turn 5 (paper):              9 messages, 50696
turn 6 (tea):               11 messages, 63537
turn 7 (coffee):            13 messages, 63720
   -> I couldn't complete that turn. Smithers web agent failed (HTTP 413): Request body is too large.
```

From that point:

- Every later turn fails the same way, including `say ok`.
- **`/clear` cannot recover it.** `/clear` runs a model turn first ("Reviewing
  the conversation for what to keep…") to decide what to sweep into World, and
  that turn hits the same 413:
  `"/clear didn't run — I couldn't finish reviewing the conversation, so I left it exactly as it was. Try /clear again in a moment."`
  Retrying never helps: the transcript only grows.
- The only escape observed is clearing the origin's storage at the browser level
  over CDP (`Storage.clearDataForOrigin`, the mechanism in
  `scripts/live-store-reset.ts`), because the transcript is persisted to OPFS.
  A user has no in-app equivalent — the admin-only `/reset` is not offered to a
  non-admin login.
- Scrolling and the composer stay responsive throughout (fill 76ms, ten scroll
  jumps 187ms at 16 messages), so the failure is the seam, not the renderer.

The message is honest about *what* failed, so this is not a §4.10 blank-bubble
defect. It is that there is no transcript trimming, no summarisation, and no
recovery path — the conversation is permanently dead. `/retry` makes it arrive
sooner, because each retry re-posts the user message (see [4.6](./4.6.md)).
