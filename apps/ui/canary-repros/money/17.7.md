# 17.7 — the admin grant surface: one clause diverges, two are unreachable

Origin: <https://canary.smithers.sh> (bundle `assets/index-BHHXuMoZ.js`)
Billing upstream: <https://billing.smithers.sh> (worker `smithers-cloud-billing`,
version `27fbf30e-102c-4318-9366-eadb935f1a66`, deployed 2026-08-19T04:58:55Z)
Account: `codeplanesmithers` (allowlisted, `admin:false`)
Tested: 2026-08-19, money lane round 1

## Checklist row

> **17.7** `[auto E-1..E-3]` Admin grants: no token → 401, untimestamped → 400,
> valid grant credits exactly once with an audit record.

## Steps

1. `POST https://billing.smithers.sh/api/billing/admin/grants` with a JSON body
   and NO admin token.
2. Repeat with `x-smithers-admin-token: <the deployed ADMIN_SERVICE_TOKEN>` and
   no `timestamp` field.
3. Repeat with `requester` + `timestamp` + a stable `grantId`, twice.
4. On the canary, `POST /api/admin/grant` with the non-admin session.

## Expected

401, then 400 `timestamp_required`, then 201 once and a non-crediting replay
with the grant's audit attribution (`requester`, `requestedAt`) recorded.

## Actual

| clause | result |
| --- | --- |
| no token → 401 | **403 `{"error":"Forbidden origin"}`** |
| untimestamped → 400 | **not exercised** — needs the deployed admin token |
| credits exactly once + audit | **not exercised** — needs the deployed admin token |
| (extra) canary `/api/admin/grant` as a non-admin | 404 `{"status":"error","message":"Not found."}` — correct, non-enumerable |

### Clause 1: 403, not 401

`workers/billing/src/index.ts:1348-1359`: the origin gate runs before the
handler, and an origin-less request only counts as a `serviceCall` when the
`x-smithers-admin-token` header is **present**:

```ts
(url.pathname === "/api/billing/admin/grants" && request.headers.get("x-smithers-admin-token") !== null)
...
if (origin === null && !serviceCall) return json({ error: "Forbidden origin" }, 403)
```

So the refusal is by origin, not by credential: no header → 403, header present
but wrong → 401 `{"error":"Unauthorized admin"}` (verified). Nothing is
credited either way, so this is a contract divergence from the row, not a money
leak. Decide which answer is intended and align the row (or the gate).

### The automated rows E-1..E-3 cannot pass as written

`apps/ui/src/launch-checklist/Rows.ts:660-724` sends the admin credential as
`authorization: Bearer …`. The worker reads only `x-smithers-admin-token`
(`src/index.ts:701`), so E-2 and E-3 always get 401, never the 400/201 they
assert. E-3 also sends `idempotencyKey`, while the worker requires an
`admin:`-prefixed `grantId` (`ADMIN_GRANT_ID`) and answers 400 without one.
Fixing the row means changing the header and the field name.

### Clauses 2 and 3 are blocked on a credential

Billing's deployed `ADMIN_SERVICE_TOKEN` is a Cloudflare secret and cannot be
read back. `workers/billing/DEPLOY.md:46` names the holder: "operator (will
holds the copy that grants money)". Checked and ruled out:

- `workers/billing/.dev.vars` — present, but the local value is NOT the deployed
  one (a grant with it answers 401 `Unauthorized admin`).
- GCP Secret Manager, project `plue-prod-1771780303` — 72 secrets, none is a
  billing or identity admin token.
- The canary's own admin surface (`POST /api/admin/grant`, which already holds
  `BILLING_ADMIN_TOKEN`) requires an `admin:true` session. `admin` comes from
  the identity worker's `ADMIN_LOGINS` var, currently `roninjin10`
  (`workers/identity/wrangler.jsonc`). Adding `codeplanesmithers` needs an
  identity redeploy, which this verifier lane must not do.

Rotating the secret would unblock the row but would break the operator's copy
and the product Worker's matching `BILLING_ADMIN_TOKEN` at the same time, so it
was not done.

## What a human must do

`CHECKLIST_BILLING_ADMIN_TOKEN`, or add a grading login to identity's

it grades all three clauses when the token is present.
