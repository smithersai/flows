# 19.3 — a failing composer flow raises no toast

Origin: <https://canary.smithers.sh>  ·  Account: `codeplanesmithers`  ·  Tested: 2026-08-19

## Checklist row

> **19.3** Toasts appear for the events that warrant them, stack without
> overlapping, and auto-dismiss.

## What passes

Stacking and auto-dismiss are correct. Two toasts open at once
(`Read developer.mozilla.org` at y 816–861 and
`Reviewing the conversation for what to keep…` at y 869–934) do not overlap,
and `ok` toasts dismiss themselves after ~4 s.

## What fails

The first clause. A flow the user typed into the composer that FAILS produces
no toast at all.

| flow | real failure | toasts seen | transcript changed |
| --- | --- | --- | --- |
| `/keys.list` | `GET /api/user/byok-keys` → 404 | 0 | no |
| `/billing.upgrade` | `POST /api/billing/checkout` → 400 | 0 | no |
| `/browser https://127.0.0.1/secret` | `POST /api/tools/browser-fetch` → 422 | 0 | yes (error card) |

## Root cause

Two independent holes:

1. **The composer path drops failures.** `send` in
   `apps/ui/src/mainview/state/AppController.ts:2317` runs
   `void commands.run(parsed.name, parsed.args)` with no
   `.then((outcome) => surfaceCommandFailure(name, outcome))`. The pointer
   paths `runCommand`/`runCommandArgs` (lines 4361–4371) do attach it. So a
   slash command that fails is silent, while the same flow clicked as a button
   toasts.
2. **`withToast` swallows fast failures.** `withToast` only dispatches
   `toast.shown` after a 300 ms debounce (`toastDebounceMs = 300`). If the work
   settles first, line 483 returns early —
   `if (!shown && store.collections.toasts.get(...) === undefined) return outcome` —
   so no `toast.resolved` is ever dispatched. The 422 private-host case above
   comes back in well under 300 ms and therefore never toasts.

A related mislabel: `/browser https://no-such-host-money-lane-9f3ab.smithers.sh/x`
resolves its toast to **`ok` — "Read no-such-host-money-lane-9f3ab.smithers.sh"**
while the transcript card next to it says the host could not be resolved. The
browser tool answered 200 with an error payload, so `withToast`'s
`typeof outcome !== "string"` test reads it as success.
