# 13.7 — fake success writing to a read-only repository

Origin: https://canary.smithers.sh · tested 2026-08-19 · account `codeplanesmithers`
Repro: `bun apps/ui/canary-repros/github/13.7.ts` · screenshot `/tmp/canary-github-13.7.png`

## Steps

1. Sign in on https://canary.smithers.sh as `codeplanesmithers`, which has
   read-only access to `octocat/Hello-World`.
2. `/repos.import octocat/Hello-World` — it reports DONE.
3. `/issues.create canary repro 13.7 <stamp> octocat/Hello-World`.
4. Check github.com/octocat/Hello-World for that issue.

## Expected

"Honest refusal, no fake success."

## Actual

A fake success. The card reads:

```
Issue #3 · octocat/Hello-World   DONE
#3 canary repro 13.7 1787122817001   OPEN
octocat/Hello-World · opened by codeplanesmithers
```

Nothing exists on github.com/octocat/Hello-World — GitHub search for the title
returns `total_count: 0`. The write landed in the jjhub mirror of someone
else's repository, and the mirror's issue numbering restarts at #1 while
GitHub's real `octocat/Hello-World` is at #10897.

`/issues.close 1 octocat/Hello-World` behaves the same way: the card flips to
`CLOSED` for an issue no one outside the mirror can see.

There is a second, earlier shape of the same row: run the writes **before** the
import job completes and they are silent instead — no card, no toast, no
message (same root cause as 13.4). Neither shape is an honest refusal.

## Route and selector

- Flows: `issues.create`, `issues.close`, `issues.comment`; card
  `[data-kind="issue"]`.
- Route: `POST /api/repos/octocat/Hello-World/issues` → `201 Created` from the
  jjhub platform. GitHub's own permission model is never consulted.
