# 14.3 — `/prs.create` is silent with and without `from:<bookmark>`

Origin: https://canary.smithers.sh · tested 2026-08-19 · account `codeplanesmithers`
Repro: `bun apps/ui/canary-repros/github/14.3.ts` · screenshot `/tmp/canary-github-14.3.png`

## Steps

1. Sign in on https://canary.smithers.sh.
2. `/prs.create Canary repro 14.3 with bookmark from:canary-read-only-summary codeplanesmithers/canary-sandbox`
3. `/prs.create Canary repro 14.3 without bookmark codeplanesmithers/canary-sandbox`

## Expected

- With a valid bookmark: a pull request opens and the `[data-kind="pr"]` card
  appears.
- Without one: the honest message `LandingsSeam.createLanding` already returns —
  `prs.create needs a source branch — run /branches.list, then /prs.create <title> from:<bookmark>`.

## Actual

Both forms are completely silent: no card, no transcript growth, no toast, and
the landing count on the platform is unchanged.

## Route and selector

- Flow: `prs.create`; card `[data-kind="pr"]`.
- Routes read: `GET /api/repos/{o}/{r}/bookmarks`, `GET …/changes?limit=100`.
- Route that would be written: `POST /api/repos/{o}/{r}/landings`.

## Why nothing is created

`createLanding` derives the change stack with
`deriveBookmarkStack(changes, source.targetChangeId, targetRow.targetChangeId)`
and refuses when the walk is empty. In `canary-sandbox` the source bookmark
`canary-read-only-summary` (`krxsvnwz…`) has parent `lxktpptp…`, while `main`
points at `wuswlqkx…`, so the walk from source never reaches main's tip and the
stack comes back empty. That is an ordinary situation for a branch cut before
main advanced, and the seam's own answer — `Couldn't derive the branch's change
stack.` — is reasonable.

The platform accepts the same landing when it is posted directly:
`POST /api/repos/codeplanesmithers/canary-sandbox/landings` with
`change_ids: ["krxsvnwzowtnktnoxzqwytlqlsmutlun"]` returned `201` and created
landing #2. So the refusal is the seam's, not plue's.

**The defect on this row is that the user is told none of it.** Both refusals
are dropped by the composer's `send` path — see 13.4.md for the shared root
cause.
