# 14.5 — the landing the card queues is not a GitHub pull request

Origin: https://canary.smithers.sh · tested 2026-08-19 · account `codeplanesmithers`
Repro: `bun apps/ui/canary-repros/github/14.5.ts` · screenshot `/tmp/canary-github-14.5.png`

## Steps

1. Sign in on https://canary.smithers.sh.
2. Open a landing in `codeplanesmithers/canary-sandbox` (the repro creates one).
3. `/prs.land <n> codeplanesmithers/canary-sandbox`.
4. Compare the card against github.com.

## Expected

"Queues the merge and the card reflects the queue state, not a claimed merge.
Confirm the claim matches GitHub."

## Actual — the queue-state half is right

The card flips to `QUEUED` and never claims a merge. It is conservative: it
still reads `QUEUED` after the platform has already recorded the landing as
`merged`. No false merge claim.

## Actual — the GitHub half does not hold

The thing being landed is a jjhub landing on `api.jjhub.tech`, not a
github.com pull request:

- After landing, github.com/codeplanesmithers/canary-sandbox's default-branch
  head is unchanged (`d77d8f5c`), and its one open pull request
  (#2 "Canary: read-only repository summary") is still open.
- The landed title cannot be found on GitHub at all
  (`search/issues … type:pr` → `total_count: 0`).
- The numbering collides. The card is titled
  `Pull requests · codeplanesmithers/canary-sandbox` and lists `#1`, `#2`, `#3`,
  which are mirror landings. github.com's pull request `#2` in the same
  repository is a different object that these flows never touch.

So a user reading "Pull requests · codeplanesmithers/canary-sandbox — #4 …
QUEUED" would reasonably conclude a GitHub pull request is queued to merge.
None is.

## Route and selector

- Flow: `prs.land` (user-only); card `[data-kind="pr"]`, button
  `data-flow="prs.land"` labelled "Land (queue merge)".
- Route: `PUT /api/repos/{o}/{r}/landings/{n}/land`.
