# 14.6 — an unmergeable land is refused by the platform and the app names no reason

Origin: https://canary.smithers.sh · tested 2026-08-19 · account `codeplanesmithers`
Repro: `bun apps/ui/canary-repros/github/14.6.ts` · screenshot `/tmp/canary-github-14.6.png`

## Steps

The repro builds the fixture itself and restores it afterwards:

1. `PATCH /api/repos/codeplanesmithers/canary-sandbox`
   `{"landing_queue_required_checks":["ci/canary-required"]}`.
2. `POST …/landings` to open a landing on the newest change.
3. `POST …/statuses/{change}` `{"context":"ci/canary-required","status":"failure"}`.
4. Type `/prs.land <n> codeplanesmithers/canary-sandbox` and submit.
5. `PATCH` the repo back to its previous `landing_queue_required_checks`.

## Expected

"Honest refusal naming the reason."

## Actual

The card stays `OPEN`, the transcript does not grow by a character, and no
toast is raised. The platform's answer, taken on the same page immediately
after, is exactly the sentence the user should have seen:

```
PUT /api/repos/codeplanesmithers/canary-sandbox/landings/5/land
-> 422 {"message":"required status checks are not passing: ci/canary-required"}
```

Note the card *does* show the failing check in its Checks section
(`ci/canary-required  FAILED`), so the data is on screen — but pressing Land
produces no visible outcome at all, successful or refused.

Without a required check configured, the same repository lands a PR that has a
`failure` status and an outstanding `request-changes` review without complaint
(`landing_queue_required_checks` was `[]`), so the refusal path only exists once
required checks are set.

## Route and selector

- Flow: `prs.land`; card `[data-kind="pr"]`, button `data-flow="prs.land"`.
- Route: `PUT /api/repos/{o}/{r}/landings/{n}/land` → `422`.

Shared root cause with 13.4 / 14.3 / 14.4 — see 13.4.md.
