# 13.4 — `/issues.view` on a missing number says nothing at all

Origin: https://canary.smithers.sh · tested 2026-08-19 · account `codeplanesmithers`
Repro: `bun apps/ui/canary-repros/github/13.4.ts` · screenshot `/tmp/canary-github-13.4.png`

## Steps

1. Sign in on https://canary.smithers.sh.
2. Type `/issues.view 99999 codeplanesmithers/canary-sandbox` and submit.

## Expected

An honest message. `IssuesSeam.showIssue` already returns exactly one for a 404:

```
Issue #99999 in codeplanesmithers/canary-sandbox answered 404. If … isn't imported,
only the issue list can read from GitHub — issue detail needs the import: run /repos.import …
```

## Actual

Nothing. No card is added, the transcript does not grow by a single character,
and no toast is raised. The only trace is a `404` in the network log. The user
cannot tell whether the flow ran.

`/prs.view 99999 <repo>` behaves identically.

## Route and selector

- Flow: `issues.view`; composer `textarea.smithers-composer`.
- Route: `GET /api/repos/{owner}/{repo}/issues/99999` → `404`.

## Root cause (shared with 14.3, 14.4, 14.6)

`AppController.surfaceCommandFailure` turns a failed flow into a toast, but it
is wired only into `runCommand` / `runCommandArgs` as called by the **slash
menu**. A flow typed with arguments never reaches that path: the composer's
`onSubmit` calls `controller.runCommandArgs("send", text)`, and the inner
flow's returned error string is dropped inside the `send` flow.

Verified side by side in one session:

| how the flow was submitted | result |
| --- | --- |
| `/prs.land` bare, chosen from the slash menu | toast: `/prs.land didn't run` + `prs.land needs a pull request number` |
| `/repos.app codeplanesmithers/no-such-repo-xyz` (typed with an argument) | silent |
| `/issues.view 12345 codeplanesmithers/demo-calendar` (typed with an argument) | silent |

Every §12–§14 flow that takes an `owner/repo` or a number must be typed with
arguments, so every honest refusal in this lane is invisible on the canary.
