mvp × Agent Chain — integration & debug-mode plan

2026-08-11 · sources: flows/docs/specs vault (Agent Chain, Chain Slice, Chain Harness Build, Product Surfaces, System Prompt, Forensics, Notification Queue, Temporal Worldview) · flows/agent package survey · full ~/mvp code map · tickets #17 mvp-harness-transport / #18 mvp-session-model

TL;DR. The mvp's current agent is one HTTP POST to chat.smithers.sh with a client-side tool loop — a ticketed violation of the Product Surfaces mandate. The replacement, the Agent Chain (@smthrs/chain), shipped today with PRs 1–8 landed and is browser-runnable now: QuickJS sealed runner, model seat, catalog, memory door, sub-chains, envelope seam. The plan: run the concierge chain in the webview behind the existing NativeAgent seam, project the mvp command registry as the catalog, persist the chain journal into the existing OPFS store, and grow the AgentTurnFrame envelope into a projection of chain events. The UI stays what the vault says it is — folds over one event stream — and debug mode is the same fold at full fidelity: script x-ray, two-histories diff, cache-hit build view, prompt inspector, wire tap, journal scrubber.

The five chain gaps the integration must bridge (from the package survey): (1) no live event stream from Chain.run; (2) no durable journal binding; (3) ControlExecutor is a noop — Control/gateway is contracts, not wiring; (4) two event vocabularies (cell AgentEvent × chain Event) and an untyped Control wire event; (5) steering's durable binding (@smthrs/notifications) unwired, no monitor/wake.

The convergences that make this cheap rather than hard: mvp already is a TanStack-DB fold with an actor-stamped transition journal; the command registry already is a catalog with visibility rules (agentVisible()); worldDocuments already is the worldview wiki the System Prompt describes; and the NativeAgent seam is four members wide.

Why the concierge runs in the browser: the System Prompt's BASE section states it (“the brain of an agentic harness that runs in the browser”), the chain's dependency set has no Node built-ins, and the QuickJS runner ships the browser-safe single-file variant. The webview is where the catalog's most valuable entries live anyway — every UI command. Heavy/repo work is a sub-chain with server placement, which is a catalog call like any other (Agent Chain §Nesting), reached initially through the existing workflow relay and eventually through Control.

The only mandatory new server surface is /api/model/stream: a metered worker route that speaks the full ModelEvent vocabulary (text/thinking deltas, usage, settle). The current {delta, done} proxy cannot carry a sealed step. Same auth/metering pattern as the existing turn route; the turn relay itself and the cancellation Durable Object retire (cancel becomes lineage interruption in the runtime that owns the fiber).

3 · The seam plan — what changes, what dies, what survives

The envelope grows; it does not get replaced

AgentTurnFrame stays the one wire the UI folds, extended with a chain family (a zod-union edit plus frame-handler branches — the extension path the code already anticipates). runId becomes the lineage id, resolving the identity overload (turn id = cancel key = message prefix) in one move and setting up ticket #18's session model.

  delta · done · card · card.update · tool_call            (existing — tool_call retires with the loop)
+ link.authored   { link, scriptDigest, script }           ← LinkAuthored
+ call.started    { link, ordinal, name, payload }         ← runtime, pre-settle
+ call.settled    { link, ordinal, name, verdict: run|hit|replay, resultDigest }
+ gate.rejected   { link, kind: shape|fuel|catalog|denied|call_failed|script_failed }
+ link.ended      { link, outcome: done|to|park(code) }
+ steering.drained{ link, count }
+ park            { code: approval|event|timer|quota|plugin, approvalCard? }

What is deleted (the satisfying column)

  • src/bun/CloudAgent.ts, src/server/AgentApi.ts, the worker turn relay + TurnCancelRegistry DO — the proxy transport, whole.
  • Instructions.ts → Prompt.assemble (byte-stable, cache-tested, source-of-truth in the vault).
  • RunClaims.ts + claimBuffer — regex claim-substitution exists only because the model returns unstructured prose beside real effects; chain outcomes are typed, so the turn-settle path rewrites onto link.ended/terminal events. (Careful: settleRunClaims is load-bearing in four paths today.)
  • agentTools.ts's one-tool projection, toolItems/MAX_TOOL_LEGS bookkeeping, transcript re-send per leg — control flow moves into the authored script, which is the whole point (“one turn does what took a dozen tool-call turns”).
  • The /clear sweep as a bespoke second model call — it becomes an authored flow that reads a transcript projection and writes worldview notes through remember.

What survives untouched (the load-bearing column)

  • AppStore/AppState — chain events are new collections + transitions; the dispatcher, journal, persistence, and actor stamping don't change.
  • The command registry, the parity test (“every affordance is a command”), slash menu, pills — commands become catalog entries; trigger: "user"|"agent"|"both" becomes the catalog visibility predicate it already is.
  • App.tsx/ChatCards.tsx and all 18 card kinds; toasts; auth/billing/reco/workflow seams; the browser-fetch tool.
  • The card frame path (card/card.update) — already validated and wired; the chain uses it as the widget door. “Show, don't just say” lands as typed cards first; free-form generative HTML stays a later, separately-decided card kind.

4 · Phases, each with its bar

Phase 1 Chain behind the seam, feature-flagged

  • Link @smthrs/chain + @smthrs/model via the donor file: pattern (the ui submodule's wiring; mind the Bun file:-tarball trap → bun pm migrate workaround).
  • New ChainRuntime in mainview implementing the NativeAgent surface: startTurn = Chain.run; cancel = fiber interrupt; subscribe = the event fold.
  • Journal = chainEvents TanStack collection (OPFS), honestly labeled an app-layer stand-in for the engine journal; replay-on-reload comes free from the chain's own replay rule.
  • Catalog v1: command projection + sys/* + card.show. Worker gains /api/model/stream.
  • Flag: session.agentBackend = "proxy" | "chain", flipped by an admin command; both backends behind the same seam until parity.
Bar (ticket #17's, upgraded): a chat turn driven by the chain end-to-end — model deltas render, the authored script exists in the journal, calls execute as real commands with actor smithers, a gate rejection is visible as an observation the next link corrects, reload mid-turn replays with zero re-executed model calls and zero re-executed effects.

Phase 2 Steering, approvals, background work, triggers

  • Composer stays live during a turn: mid-turn input → Steering.admit, drained at link boundaries, rendered as steering.drained markers.
  • Authorize.layerRules encodes the three-tier policy (free / ask-once-per-session-revocable / outbound-always-asks). approval_required park → existing approval card; approve resumes the lineage, which re-executes the link from its settled prefix — this is the semantic the chain's PR 8 already ships.
  • agent catalog entry with background: true → own lineage; its monitor is a notification admitted to the concierge's steering queue (system-event class) — “never block on slow work” becomes mechanical.
  • Triggers v1: UI + slash (already the registry), schedules via @smthrs/triggers cron on the worker, webhooks as channels terminating at the worker → notification admit. triggers.register is a catalog entry; the trigger inventory lives in worldview, as BASE promises.
Bar: user steers mid-turn and the next link's context contains it; a chat-side outbound effect asks first, every time; a backgrounded sub-chain completes and the concierge surfaces the result unprompted; a cron trigger starts a chain with nobody watching.

Phase 3 Worldview convergence

  • Bind remember/recall to worldDocuments: recall = scored query over the wiki (keyword first, FTS when browser SQL lands); remember = note upsert with provenance, confidence, actor. The agent's scripts literally read memory from world — the ask, verbatim.
  • Retrieval flows the agent authors and saves (“flows written in the past for retrieving from it”) = registry entries persisted as world documents with a flow tag — the first real instance of the agent extending its own catalog.
  • Adopt @smthrs/memory's store underneath when the flows browser-SQL layer ships; the wiki becomes the notes-lane surface. Watch the documented catalog double-declaration hazard (one remember disclosed, a different one run → resume-breaking digest mismatch).
Bar: a fact learned in one conversation is recalled in a fresh one via a script-authored recall call, with confidence and provenance visible; the /clear sweep is an ordinary authored flow.

Phase 4 Control alignment — closing #17/#18 in their final form

  • When the flows engine mounts under chain (journal binding + trampoline in the engine), the chainEvents collection stops being locally appended and becomes fed by the flows-owned sync layer — the exact data path Ui.md settles. The UI code doesn't change: same collections, same folds.
  • Sessions keyed by lineage ids; run list via Control.List; attach/detach via Watch cursors; server-placed sub-chains observed through the same envelope.
Bar: kill the tab mid-run on a server-placed chain, reopen, attach by lineage id, and the transcript is identical to having watched live.

5 · Decision points for will

D1 — model transport. New /api/model/stream route speaking full ModelEvent (recommended; the {delta,done} proxy cannot carry a sealed step) vs extending chat.smithers.sh's vocabulary. Either way it stays metered per user.
D2 — worldview binding order. worldDocuments-backed recall now (product-visible, already built, zero new storage) vs waiting for @smthrs/memory in the browser. Recommended: wiki now, SQL store underneath later — the catalog entry names and schemas stay fixed either way, so scripts don't churn.
D3 — the journal stand-in. OPFS collection journal now (recommended — it's the same honesty as Journal.layerMemory, plus persistence) vs blocking Phase 1 on the flows engine mount. Guard against it becoming a second engine the same way the Chain Slice did: acceptance tests assert journal contents, not runtime API.
D4 — widget door scope. Typed cards only (recommended for v1; 18 kinds exist and the frame path is validated) vs an agent-authored-HTML card kind (sandboxed iframe srcdoc). The concierge prompt promises widgets; typed cards deliver that promise without opening the generative-HTML question mid-migration.

6 · Upstream work in the agent/flows repos (fix at the source)

  • Chain event tap: Chain.run needs a live Stream<Event> (or a blessed Journal.layerTee) — today a UI can only poll Journal.read. This is gap #1 and it belongs in @smthrs/chain, not in mvp.
  • Type the Control wire event: ControlEvent.kind is an untyped string with an opaque payload; the chain's six-event union is the natural typed vocabulary for Watch, and Phase 4 depends on it.
  • Steering's durable binding: wire @smthrs/notifications' queue under Chain.Steering (the in-memory drain has an acknowledged loss window).
  • Park/wake: ParkCode includes event/timer but nothing wakes a parked chain — the monitor story in Phase 2 needs at least the approval-resume and background-completion wakes; flag the rest into the vault's open question rather than inventing it in mvp.

7 · Debug mode — the same fold, at full fidelity

The design principle comes straight from the vault: forensics are queries, not commands (Forensics.md), and the UI is a fold over the journal. Debug mode is therefore not instrumentation bolted on — it is rendering, at full fidelity, evidence the app already persists for correctness: chainEvents, transitions (actor-stamped), toolCalls, and the model-event ring. One toggle (/debug, admin-gated and non-enumerable, evolving today's DevtoolsPanel), seven surfaces:

Rules that keep it honest

  • Read-only. Every debug surface is a query; mutating verbs (retry a link, fork) arrive only as first-class chain verbs later, never as debug-panel side doors.
  • Evidence, not claims. Views report recorded evidence and its last sequence; after a crash, absence of an event is shown as absence — never “this didn't happen” (Forensics' journal-boundary rule).
  • Commands all the way down. Each surface is a command (/debug.links, /debug.context, /debug.net …) so the parity discipline holds and the agent itself can be asked to open its own x-ray.
  • Bounded. Model-event ring keeps the last N turns raw; chainEvents gets the same compaction discipline as messages; the wire tap only records while debug mode is on.

8 · Risks and traps

  • Bun × file: transitive tarballs — the 24/100 POC's biggest wound; use the bun pm migrate workaround, budget for it in Phase 1.
  • Catalog double-declaration — one entry disclosed, a different one run breaks resume across the digest mismatch; the memory door and registry projection must mount exactly once each.
  • Steering loss window — until the notifications queue is wired, an in-memory drain can lose a steer on crash; acceptable behind the flag, not at parity.
  • OPFS budget — journals grow monotonically; compaction/truncation policy needs deciding before the flag flips default (the vault's Journal Truncation note is the reference).
  • Concurrent sessions — two live Claude sessions are actively rebasing the agent and flows stacks; pin the chain package by commit for Phase 1 and re-sync deliberately, not continuously.
  • Don't fork the vocabulary — any frame/field mvp needs that chain doesn't emit goes upstream as a chain event first (§6); mvp never invents private chain semantics (the exact mistake @smthrs/core's duplicate Flow was).
