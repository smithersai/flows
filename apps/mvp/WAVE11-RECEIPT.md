2026-08-09/10 (UTC) · run `oneshot-wave11-workflows` · branch `oneshot-mskp7qe7-work` (~/mvp)

**Bottom line:** the product no longer says it can't. Asking "can you make me a smithers workflow that summarizes my open issues?" in the chat now provisions **this user's** workspace gateway on Smithers Cloud, launches the stock `create-workflow` on it with the user's own words, and renders an **embedded run card** that tracks the real run live from the relay's event stream. Proven on the real relay against `codeplanesmithers/smithers-demo`: gateway `6b7ca340-1843-4d5a-85bc-cb5b6c341d5a`, runs `4c3696f2-d712-42ca-aa38-db701e84d9c2` and `ab6555b2-8f60-4dcb-b676-e29ddd19e863`. Deployed as `smithers-mvp-web` version **`391a0e4d-781e-4e9b-a923-1c22e3cc1494`** (the wave shipped as `6a0329e4-…`; §4a's review-pass fixes are what advanced it).

**And the honest half:** the happy path — a workflow that actually gets created — **does not complete today**, for a reason outside this wave. Every agent node on a workspace gateway VM dies instantly with *"Smithers generated an OpenRouter default agent, but OPENROUTER_API_KEY is not set"*. `create-workflow` is nothing but agent nodes. WAVE4-RELAY-RECEIPT.md §2 said this in passing ("no agents — gateway VMs carry no AI-provider credential"); this wave is the first to hit it in the product. The seam is right and the card is truthful about the failure. The workspace cannot yet do the work. That is the launch blocker, and it is one credential on the VM image, not a rewrite.

## 1. The gateway seam, per user

`src/worker/gateway.ts` (new) implements WAVE4-RELAY-RECEIPT.md §5 faithfully, server-side only:

- **The door → the gateway.** `POST {IDENTITY_UPSTREAM_URL}/api/identity/cloud-token` (service token, by login — the wave-11b contract, including its typed `{found:false, cloud:{status}}` honesty) → `POST {SMITHERS_CLOUD_API_BASE_URL}/api/repos/{owner}/{repo}/gateway`.
- **Idempotent provision-or-resume**, re-called freely; the returned `gateway_id`/`token`/`base_url` are **always** adopted (§5 item 3 — a reprovision legitimately hands back a different gateway). Re-resolve at the **half-life** of the issued window, with a floor so a bogus `expires_at` cannot spin the provision loop.
- **The taxonomy is distinct and never retry-looped**: `401` → re-mint the Cloud token through the door and retry **exactly once**; `409` → `provisioning` for the caller to poll; `500 no_capacity` → surfaced as itself ("nothing was queued; try again in a bit").
- **Tokens never reach the browser.** Per-user records live in a Durable Object keyed by login (`GATEWAY_SESSIONS`, migration `v2`). The browser talks only to `/api/workflow/*`; the Worker sets the `Authorization` header a browser structurally cannot (WAVE4 §3c's caveat).
- **The relay surface is an allowlist** — `listWorkflows`, `launchRun`, `getRun`, `listApprovals`, `submitApproval`, `getNodeOutput`, `whatHappened`. Nothing else crosses, and a malformed `repo` is refused before any upstream call.
- **Streaming.** `/api/workflow/events` relays `GET /v1/api/runs/{runId}/events?afterSeq=` (the REST projection of `streamRunEvents`); `/api/workflow/stream` proxies the relay SSE end to end and forwards `Last-Event-ID`. The client's pump resumes from the card's persisted `lastSeq`, so the 600s relay cap is routine, not exceptional — two consecutive read failures flip the card to an honest **reconnecting** state, and the pump never stops silently.
- **Approvals** name their repo and round-trip through that user's gateway (`/v1/rpc/submitApproval`); a repo-less decision keeps the static `GATEWAY_UPSTREAM_URL` mode for the local stub stack.

## 2. Workflows in the conversation

Three commands, `trigger: both`, three-way invocable (slash · agent tool · the list card's Run binding) — and nothing else was added:

- **`workflow.create <description>`** — provision (toast), then launch the stock `create-workflow` with `input: {prompt: description}`.
- **`workflow.list`** — the workspace's workflows as an embedded card.
- **`workflow.run <name> [owner/repo]`** — launch + the same run card.

The run card (EMBED LAW) carries live phase, node progress **in words**, the result leading once it settles, and routes any approval through the existing round trip. The watched set is the universe: a repo outside it opens the wave-10 chooser instead of guessing, and nothing is provisioned.

### The decision: `create-workflow`, not file-writing

The brief allowed either. `listWorkflows` on the live gateway settles it — the global pack is really there:

```
["chat","create-skill","create-workflow","docs-driven-development",
 "oneshot","smithers-repo-federation","whole-foods-meal-planner","workspace"]
```

`create-workflow` takes exactly `{prompt}` (`.smithers/workflows/create-workflow.tsx:64`), which is the user's sentence unchanged. Writing a `.tsx` by hand would need a workspace file-write path that does not exist in the allowlisted RPC surface, and would produce a worse workflow than the one the stock pack is built to produce. So: **launch `create-workflow`**. That decision stands; it is the *execution* of its agent nodes that is blocked (see honest gaps).

## 4. What the live run found — three defects the doubles could not have

Every one of these was invisible to a stub and fatal in production. All three are fixed, each with a regression test that fails without its fix.

1. **The run card narrated nothing, because the event vocabulary was wrong.** The engine emits `RunStarted` / `NodeStarted` / `NodeFinished` / `NodeFailed` / `NodeRetrying` / `NodeWaitingApproval` / `ApprovalRequested` / `RunFinished` / `AgentTraceEvent` — PascalCase — not the dotted names the client parsed. Live, the card sat on its launch line forever while a real run moved underneath it: a silent stall, the exact thing §1 forbids. Now it speaks the engine's own vocabulary, `FrameCommitted`/`SnapshotCaptured` stay silent as machinery (the cursor still advances past them), and an `AgentTraceEvent` capture-error becomes the card's honest sentence.
2. **A run whose nodes had failed reported `status:"running"` forever.** Live `getRun` returned `status:"running"` with `summary:{failed:1}` — a card gated on `status` alone polls that until the tab closes. The terminal **event** (`RunFinished`/`RunFailed`) is now authoritative, and a failure leads with the engine's own reason rather than a shrug.
3. **A stale gateway record was a permanent dead end.** A cached record pointing at a gateway that no longer answers failed every call with "Network connection lost" and never recovered. §5 says a VM can idle-suspend or be recycled, so unreachable is stale state, not a dead end: it now forces exactly one re-provision and retry — the same bounded policy as a 401 — and the reason is stated instead of swallowed. (Found because the Worker's DO persisted a record across a `wrangler dev` restart; the same shape occurs in production whenever a VM is recycled.)

### 4a. Review pass — four more, three of them only the live relay could show

Found reviewing this wave's own diff and re-running the live check against canary. All fixed, each with a regression test that fails without its fix.

4. **A suspended workspace was a permanent dead end after all** — the same defect as (3), through the door (3) did not close. Re-running the live check hours later, **every** relay call to the still-cached gateway `6b7ca340-…` came back as a Cloudflare **502**: its VM had idle-suspended, and §5 says exactly this happens ("VM stops; the row stays `running`, so the relay keeps 200-ing until the tunnel fails. Re-POST resumes it"). A 502 is neither a thrown fetch nor a 401, so nothing re-provisioned: the run card sat in *Reconnecting* and `/api/workflow/provision` cheerfully answered `ready` **from cache** — the client could not force a resume even by asking. A relay `502/503/504` now joins the 401 and the unreachable base_url in forcing exactly ONE re-provision and retry, with two bounds: a record minted in the last 30s is not re-POSTed again (an `EventSource` reconnecting every few seconds must not stampede the provision route), and a call a repeat could duplicate (`launchRun`) is **not** replayed — the workspace is resumed for the next attempt and this one is reported as what it was ("Your workspace had gone to sleep. It is awake again — ask me once more.").
5. **`..` was a legal repository name, and it steered the Cloud token.** `REPO_NAME_PATTERN` allowed any `[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+`, which `../admin` and `../..` both satisfy — and URL parsing resolves them away, so `POST /api/repos/../admin/gateway` becomes `POST /api/admin/gateway`, carrying the user's **server-held** Cloud token to a route this seam never allowlisted. Holding the token server-side is pointless if the browser still chooses where it is spent. `isRelayRepoName` now refuses any `.`/`..` segment (dot-*prefixed* names like `.github` are real repositories and stay legal), at the routes **and** inside `ensureGateway`, so no caller can reopen it.
6. **A gate the engine announced could get no approval card.** `listApprovals` was fetched only when `getRun` reported `runState.blocked.kind === "approval"` — but `runState` is *derived*, and the gateway computes it best-effort (`computeRunStateFromRow(...).catch(() => undefined)`), so a genuinely parked run can read as plain `running` with no `blocked` at all. The human would then see a card saying *Running* and no way to unblock it, while the run waited on a decision it never asked for. The engine's own `NodeWaitingApproval`/`ApprovalRequested` **event** is now an equally authoritative trigger (the same lesson as (2), one gate over), retried until the approval row is actually in hand; the card reads *waiting-approval* whenever an undecided approval for the run is in the transcript. An approval row that arrives without an `iteration` is defaulted to 0 rather than dropped — dropping it stranded the run.
7. **The in-isolate record key could collide across users.** `${login}${repo}` gave `("ab","c/d")` and `("a","bc/d")` one entry — one user's operator token answering another's call. The Durable Object path is unaffected (records are keyed inside a per-login DO), so this was latent, not live; the key is now separated.

**Also struck:** the pre-flight `listWorkflows` gate. The live gateway populates its global pack **lazily** — a cold call returned only `["chat","oneshot","workspace"]` and the full pack seconds later — so gating on that list refuses a workflow the workspace really has. `launchRun` resolves the registry on a miss and answers `NOT_FOUND` honestly; that is the only truthful "no such workflow", and only then is it worth naming what the workspace does have.

## 5. Honest gaps

- **The happy path is not proven, because the workspace cannot run it.** `create-workflow` launches, parks on `clarify`, and that node fails instantly — `OPENROUTER_API_KEY is not set` — then retries and fails again, live, on canary. Gateway VMs carry no AI-provider credential (WAVE4 §2). Until one is installed on the VM image (or a provider is configured per workspace), **no agent workflow can complete on a gateway**, and "at least one flow created through conversation" cannot be met. Everything above it is proven and working; this is the one thing standing in the way, and it belongs to the VM image, not to this app.
- **The model still overstates the launch.** Live, with the run card beside it saying *Running*, the assistant wrote *"The workflow "summarize-open-issues" has been created and is now running"* — it invented a name and claimed a creation that had not happened. This wave made the tool result unmistakable ("A create-workflow run has STARTED… No workflow exists yet and none may ever… Do not tell the user a workflow was created") and added the instruction, both pinned by test; the deployed model **still** rounded up. Prompt-level truth discipline is not holding here. The deterministic surface (the card) is correct; the prose beside it is not, and wave-10's §2a lesson — deterministic affordances must not route through the model — probably applies to result *claims* too.
- **`workflow.create` targets the first watched repo** rather than asking which one. The watched set is the universe and the chooser handles a repo outside it, but choosing *among* watched repos is not offered. `workflow.run` accepts an explicit `owner/repo`; `workflow.create` does not yet.
- **The watched set is a GitHub set; a gateway needs a Smithers Cloud repo.** They coincide for the canary account (all three watched repos exist on jjhub). A watched repo with no Cloud counterpart would surface the provision seam's honest failure rather than a purpose-built "this repo isn't on Smithers Cloud" state.
- **A re-POST does not always resume the VM, and then nothing in this app can.** §5 says an idle-suspended VM comes back on a re-POST to the provision route. On canary, hours after the wave-11 runs, gateway `6b7ca340-…` stopped answering entirely: the seam re-POSTs (proven — `expires_at` advances on every forced resume), Smithers Cloud returns the same `gateway_id` **200 OK**, and the relay behind it keeps answering 502. The product does the contractually correct thing once per call, bounded, and states the failure; recovering a wedged VM is a Smithers Cloud concern (the row needs discarding so the next POST provisions a new gateway rather than resuming a dead one). Until then that workspace is unusable and the card sits in its honest reconnecting state.
- **A run that never terminates keeps its pump polling.** The card is truthful throughout (and reconnects honestly), but there is no client-side give-up for a run the workspace leaves running indefinitely — which is exactly what the credential-less `create-workflow` run does.
- **`no_capacity` was not observed live** — the canary gateway provisioned warm every time. It is proven at the Worker (unit) and through the whole client journey (worker e2e), and the honest state is what the UI renders.
- **The SSE change stream is an accelerator, not the transport.** Progress rides the polling pump with `afterSeq` resume; the stream only pokes it. That is deliberate (the poll is the floor, so a dead stream cannot stall a card), but it means the sub-second liveness WAVE4 §3b measured is not what the card achieves.
